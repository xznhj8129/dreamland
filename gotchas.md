# Gotchas

- Unused config/schema fields can be planned features, not dead code. Before removing one, check; carry it into the new schema or TODO.md.
- Code that handles a list of wing sections must not assume root first: build_asb_airplane flips downward fins tip-first.
- Do not catch broad exception types to show a friendly message: LinAlgError is a ValueError. Catch a dedicated exception class.
- A design that fails in simulation is a finding about the design. Never loosen test thresholds, soften inputs, auto-trim or change simulation models to make it pass; model changes with big implications are the owner's call, explained first.
- Approval covers exactly what the owner names. A suggestion I offered with several parts is approved only for the parts the reply mentions.
- Cut code by its exact text, never by searching for the next 'def': the next top-level def can be hundreds of lines further (classes in between).
- Before calling a servo/motor output 'already', 'saturated' or 'barely', state it against its range (1000-2000 us, centre 1500, +-500 throw) as a percentage.
- Sample anything nonlinear (control deflection, stall) densely where the aircraft actually operates; fractions of a limit (0, 1/2, 1 of +-45 deg) put a stalled column next to neutral and interpolation then lies (90x adverse yaw, 1/9 roll). Check a table against a direct solve at small values.
- Never write "exact" for a decomposition before a numerical check proves it: the symmetric/anti-symmetric control split is only exact for linear response; a check in aero_check.py caught it.
- A model matching a log can be two errors cancelling. Check each component (prop, drag) at the logged operating point, not only the end result (the old prop matched m62v1 speed vs power while making ~0 N thrust there).
- numpy's OpenBLAS spins a thread per core on small matrix products (NeuralFoil): 6x the CPU for no speedup. libs/__init__.py limits BLAS to one thread; measure CPU time (user) as well as wall time.
- Never derive, fit or adjust model constants from a real flight log to close a gap: the model leaves out countless real details. Report the gap; use published data (motorlib) as is.
- A missing part's resistance is not 0 in motorlib: its current solve assumes series resistance, and at 0 thrust rises with added resistance. Work the wiring out from the design instead.
- Grouping mass points by where they sit ignores how they are built: a part goes with what it is attached to (a prop with its motor), not with whichever section its own centroid falls in.
- An approved multi-phase plan covers every phase: verify each and continue; never end a phase asking for a go-ahead.
- Write a test by what it measures and run it on every aircraft that can physically do it; the airframe type belongs only where physics or the FC platform differ (how forward flight is entered and held), never in which tests exist.
- A script pilot's limits and gains are harness limits: before reporting a slowest speed, a power or a failure as the aircraft's, check the pilot was not saturated or oscillating (25 deg pitch cap; a yaw rate term that limit-cycled and doubled the power).
- Judge a stick-step response by its extreme during the step, not the value at its end: a strong yaw that swung back read as "wrong way".
- Every SITL run flies a written diff file. Never compose FC settings from strings in code: templates in data/inav/, the composed diff in the project's inav/generated/ (testglide could not arm at 40 deg pitch and the setting to change was invisible).
- The GUI never forces an order of operations, never adds things the owner did not ask for, and never refuses an edit with a guard: an incomplete definition is a definition error in the Log tab. Errors go to the Log tab, never a window or a text blurb in a panel (ticking powered on testglide silently unticked because no battery part existed).
